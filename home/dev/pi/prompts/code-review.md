对当前仓库做一次**全面 code review**, 并把结论落成仓库内的报告文件。
默认只读: 除报告外不修改仓库任何文件; 用户若要求顺带修复, 先出报告再单独动手。

用户传入的范围或焦点 (如有, 须优先满足): $@

## 不可违反的纪律

1. **一手证据**: 每条结论都要能指到具体位置 —— 本仓库 `文件:行号`, 加上游/依赖侧 `文件:行号` 或一条可复制的命令与其输出。没有证据的猜测只能进报告的"存疑"章节, 并写出验证方法。
2. **证据等级**: 报告里标注来源强度 —— ✅ 亲自复现 / ◐ 子 agent 实测 (有命令与输出) / ○ 静态推断待确认。三者措辞不得混用。
3. **只读**: 不改仓库文件 (报告除外)、不 `git` 写操作、不安装、不执行会改变系统或产物状态的操作 (构建/部署/切换)。临时文件只放 `/tmp` (若仓库有已 gitignore 的临时目录如 `.pi/` 且用户允许, 也可放那里)。开始与结束时各跑一次 `git status --porcelain` 作为"未改动"证明。
4. **不许用"启动交互式程序"做验证**: TUI / 编辑器 / 需要 tty 的程序在 agent 环境里会挂死 (真实翻车案例: 用 TUI 程序验证配置 → 会话超时 90 分钟)。需要"运行验证"时只用非交互手段: `--version` / `--help` / 离线上游文档 / 对二进制做字符串检索 / 读 man 页。
5. **权限被拒就换等价只读路径**, 不要绕道; 并在报告里说明哪些证据因此缺失。

## 阶段 0 — 侦察 (自己做, 不委派)

- 规模与结构: 文件数、行数、块分布 (哪些目录是主体)、构建/清单/CI 配置、已有文档与既有评审报告。
- 建立**可复现基线**: 只读形式的构建/求值/类型检查/lint (能跑就跑), 记录工具链版本; 基线失败本身就是最高优先级的发现。
- 定位**依赖的一手来源** (后续所有 lane 的证据基础): 从锁文件推出依赖的确切版本与源码位置 —— 例如 Nix: `nix eval --raw .#<config>.pkgs.path`; Node: `node_modules/`; Python: `site-packages/`; Rust: vendored 或 `~/.cargo/registry`。把路径记下来, 写进 lane 说明。
- 找出**可只读观测的运行态**, 能观测就不要推断: 单元/进程 `systemctl --user show`、挂载 `findmnt`、端口 `ss -lntu`、已安装产物 `ls`。
- **先确认取证工具的能力边界**, 再设计取证方式: 例如求值器不捕获错误、"整树内省"会被上游 `throw` 打断、某些路径被权限策略挡住 —— 不先确认就会派出跑不通的 lane。
- 先读**结构性文件** (入口、聚合器、清单、锁文件), 再决定切分。

## 阶段 1 — 清单 (交付物之一)

逐文件列出「用到哪些上游模块/选项族」, 以及该文件的职责与所属层次。
能求值就优先用求值器导出清单 (比 grep 准); 同时记录每个文件规模 (行数), 作为切 lane 的度量。

## 阶段 2 — 切 lane (按上下文预算)

- 目标: 每条 lane 用量 ≤ 该子 agent 上下文窗口的 **35%**。粗估 = 配置行数 × ~10 token/行 + 系统提示与报告开销 (~15–25k tokens), 留余量。
- 单条 lane 的配置规模参考 1.5–3k 行; 超了就再切。
- 上游阅读只做**定点**阅读 (`rg` 定位选项/API → 读声明附近 ±40 行 + 必要的分支逻辑), 禁止通读上游。
- 按子系统/目录/层切分; **跨切面主题单独一条 lane** (整体架构与一致性、文档与代码一致性、依赖与版本时效), 这条只看结构与抽样, 不复核细节。
- 每条 lane 的 scope 必须写清: 文件清单、上游来源路径、本领域检查重点 (正确性/合理性/惯用法/注释一致性/安全/时效)、以及阶段 0 发现的坑。

## 阶段 3 — 委派 (一次性提交)

- 把**共同规范**写成一个 `/tmp` 文件, 把**每条 lane 的 scope**各写成一个 `/tmp` 文件; lane 任务文本只引用这两个文件 + 几条硬规则, 避免重复长 prompt。
- 用**一次** async workflow 提交全部 lane (`runs.all([...])`); 每条 lane 选**只读 agent** (无 write/edit; 本机没有就明确禁止写入) + fresh context (不要 fork, 否则主会话上下文会被重复计入子 agent 预算); 设置 `timeoutMs` 与总量 `usageBudget` (≈ lane 数 × 单条 35% 预算)。
- 共同规范里写死: 报告格式 (A 覆盖与清单 / B 发现 / C 已核对无问题 / D 无法验证 + 结尾 `VERDICT:`)、严重度定义 (P0 构建失败或功能不可用或安全问题 / P1 行为与预期或注释不符 / P2 可读性·惯用法·冗余·注释不一致 / N 备忘)、报告长度上限 (≤200 行, 保护主 agent 上下文)、禁止事项 (改仓库任何文件含新建、git 写、安装、启动交互式程序、越权做整体汇总)。
- 失败处理: lane 超时/卡住 → 先 steer 纠正; 仍失败则**重跑该 lane** 并在任务里追加"硬性补充规则"(写清上一次为什么失败); 补跑结果单独加一节汇报, 不要静默丢弃。
- 子 agent 越权 (例如顺手把整体汇总也做了) 时: 只采纳其中**有独立证据的新增部分**, 其余不采信、不照抄。

## 阶段 4 — 主 agent 复核 (不可省)

- 对**全部 P0/P1** 与易复现的 P2 亲自跑一遍复现命令; 自己的结果与 lane 结论冲突时以自己的为准, 并把差异写进报告。
- 可信度分层: 被多条 lane 独立发现 → 提升; 只有一条 lane 给出且无法复现 → 降级为存疑。
- 复核成本控制: 优先复现"改一行就恢复功能"与"影响面最大"的条目。

## 阶段 5 — 架构审阅

按仓库整体看: 分层与边界 (职责是否错位)、重复与抽象权衡 (重复量 vs 抽象收益)、隐式约定 (例如"文件存在即生效"这类开关, 要写清它的真实语义与依赖)、升级/迁移风险 (版本升级、状态文件、隐式依赖)、文档与代码一致性。
输出两栏: **建议改进** (每条要有论据) 与 **建议保持现状** (每条要写为什么)。

## 阶段 6 — 报告 (落成文件)

- 路径 `docs/code-review-<YYYY-MM-DD>.md` (无 `docs/` 就放仓库根); 只新增这一个文件, 是否入库交给用户。
- 编号体系: `BUG-xx` 确定性缺陷 / `DOC-xx` 与上游文档或语义不符 / `RED-xx` 冗余与重复 / `CMT-xx` 注释与行为不一致 / `DRIFT-xx` 文档漂移 / `SEC-xx` 安全面取舍 / `HYG-xx` 残留与死配置; 每条带严重度。
- 缺陷要素: 位置 / 现象 / **触发与复现** (可复制命令 + 期望 vs 实际) / 根因 (引用上游 `文件:行号` 或本仓库逻辑) / 修复建议。
- 与官方文档不符的条目: 必须同时写出「本仓库哪一行怎么写」与「上游哪个文件哪一段怎么说 (可引原文)」。
- 改善建议条目: 必须给**论据** + **未来场景推演** —— "若继续按现状迭代, 遇到 X 场景时会出现 Y 问题"。
- 章节: 元信息 (日期/范围/基线/方法/只读声明) → 基线 → 模块清单 → 缺陷 (按类别) → 架构与改进 → 未验证/存疑 (每条附验证方法) → 分批修复顺序 (每批附验证方法) → 附录 (可复制的复现命令块、方法与覆盖率、证据来源)。
- 语言与风格: 与仓库文档一致 (默认简体中文); 结论先行、表格优先、事实与推测分明。

## 收尾自检

- [ ] 报告已写, 且 `git status --porcelain` 里除它 (与用户明确要求的东西) 之外没有改动
- [ ] 每条 P0/P1 都有可直接复制执行的复现步骤
- [ ] 每条"与文档不符"都指到了双方具体位置
- [ ] 每条改进建议都有论据与未来场景
- [ ] 所有未验证项都写了验证方法
- [ ] 没有把子 agent 的推测当作结论
- [ ] 报告没有堆砌无关信息 (只留能驱动决策的内容)

## 变体

- **只审某个范围**: 按范围裁剪 lane 数量 (1–3 条), 跳过不适用章节, 但阶段 0/4/6 与纪律不变。
- **顺带修复**: 先出报告; 用户确认后按报告的分批顺序改, 每批用报告里的验证方法验证并更新报告状态 (不要边审边改, 也不要把修复混进评审的同一个改动里)。
- **小仓库** (≲800 行配置): 可以不开 lane, 由主 agent 直接按阶段 0 → 1 → 5 → 6 执行, 但证据纪律不变。
